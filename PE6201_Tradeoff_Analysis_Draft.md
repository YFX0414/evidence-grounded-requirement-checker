# Evidence-Grounded Assignment Requirement Checker

**Business and technical trade-off analysis — draft (approximately 1,030 words; verify final word count before submission)**

## Problem and user
A student preparing an assignment may overlook a small but consequential requirement, such as a separate attachment or an exact prompt. The primary user is a student checking a draft against one rubric requirement before submission. The checker takes the requirement and only the supplied submission text, then returns Fully Satisfied, Partially Satisfied or Not Satisfied, short evidence quotations, and a statement of missing evidence. It is a review aid, not an official grader. A missing attachment in the input is treated as unverified, not proof that the student never created it.

## Build, buy, and alternatives
A keyword/rule-only baseline is cheap, deterministic and suitable for simple constraints such as a file extension or word count, provided trusted file metadata is available. It cannot reliably interpret varied prose or multi-part instructions. I rent Gemini 2.5 Flash through OpenRouter for the semantic comparison, while Python owns the prompt, response parsing, quote verification, scoring and evaluation. Colab supplies a runnable interface without a separate web deployment. The ground-truth CSV and result checkpoint are stored separately from the model request. There is no fine-tuning, agent loop or retrieval index: the submission text is supplied directly to the model, and the system never searches an external knowledge base. This reduces setup effort and the number of failure points. I used Python rather than a hosted playground because repeatable 60-case evaluation, independent quote checks, CSV outputs and per-call usage recording require explicit control.

The model can still misinterpret a requirement or repeat a student's unsupported assertion. Python checks whether a proposed quotation is actually present after normalizing whitespace. This verifies quotation fidelity, not whether the quoted statement proves the requirement. Invalid quotations should go to human review. The current verification score combines quotation validity and output fields; it is an evidence-quality heuristic, not calibrated model confidence. The model's own confidence number is not used.

## Data and evaluation
The original PE6201 A1 workbook has 60 requirement texts categorized as Constraint, Deliverable and Process. Those categories are not satisfaction labels. I selected 20 requirements and manually authored three short synthetic submissions per requirement: one intended for each satisfaction class. This creates 60 balanced cases, with the fixed reference label in a separate CSV. Cases S01–S10 form development (30 rows); S11–S20 form held-out testing (30 rows), grouped by requirement so no requirement appears on both sides. The answer label is never included in the API request. The majority-class baseline on this balanced dataset is 33.3% (all three classes tie). Synthetic text is short and constructed by the project author; it cannot establish generalization to long, unfamiliar submissions.

On the development cases, the initial label agreement was 27/30 = 90.0% and macro-F1 was 0.898. On the held-out synthetic test, agreement was 29/30 = 96.7% and macro-F1 was 0.967. All 60 outputs parsed and passed the implemented quote-substring check. However, those percentages compare against the *initial* reference labels, not an independently adjudicated gold standard. Three development disagreements (S03P, S08P, S10P) and the test disagreement (S20P) involve arguably weak Partially Satisfied labels: a single unmet threshold or an unverified claim can reasonably justify Not Satisfied. I did not relabel these cases after seeing predictions. After examining the development results, I clarified four ambiguous **test-only** requirement groups (S12, S13, S14, S17) before any held-out test calls; the development examples and labels remained unchanged. This intervention and the possible author bias limit interpretation of the high test score. No separate before-and-after leakage experiment has yet been performed; there are no explicit answer-label columns in the model input, but stylized wording may still leak class cues.

A ten-requirement exploratory check used my PE6203 group report as real material. It produced five exact label matches, four disagreements and one malformed response. That 5/10 is not a three-class performance estimate: the real labels contain no Not Satisfied case; report-only judgments cannot verify separate attachments or the true timing of work. The model sometimes accepted report claims about a separately submitted knowledge base or test workbook as if it had received those files. This motivated explicit evidence-scope wording. The full group report and attachments should not be posted publicly without group permission.

## Abstention and cost
The verification score is 0.85 or 1.00 in the development run. The development abstention curve showed that 0.85 accepted all 30 cases at 90.0% label agreement; 1.00 accepted 17/30 (56.7% coverage) at 16/17 = 94.1%. The prespecified procedure selected the highest coverage meeting 80% development selective accuracy, so it selected 0.85. This provides **no abstention** on the observed development or test samples, a genuine limitation. A higher threshold would trade review workload for somewhat better observed selective accuracy but would reject many correct cases. Even a score of 1.00 can be wrong (S03P); it is not a probability of correctness.

OpenRouter returned US$0.0060048 for 30 development checks and US$0.0062950 for 30 test checks: US$0.0122998 total, or US$0.000205 per synthetic check on average. Mean recorded latency was about 0.77 seconds on development and 0.83 seconds on test. The single demo call is additional. A previous ten-check full-report run reported US$0.0207317 across nine recorded-cost calls, about US$0.00230 per recorded call; one malformed response had unknown cost. Long submissions are thus materially more expensive. Provider cost fields are observed values for these runs, not a guaranteed future price.

## Responsible use and next step
The quiet failure is a valid-looking quote that repeats an unsupported statement, such as “20 tests were created,” while the 20 cases are absent. Quote checking alone does not catch this. The interface should show which materials were supplied, flag unsupported external-file and timing claims, and let a student inspect evidence before acting. Do not put API keys in GitHub. A future version could use trusted file metadata and multi-file input, improve partial-label guidance with independently reviewed cases, and evaluate actual student work with permission. Until then, outputs should guide review rather than determine marks.
